# Seed: workflow-backed implement-plan skill

> **Status (2026-07-20):** refined by the brainstorm at the end of this
> document. v1 is `implement-plan-workflow` — a thin interactive skill plus a
> versioned workflow script that runs one `implement-phase` worker per phase
> with a smart gate agent between phases. The workflow research below is the
> implementation reference.

## Goal

Create a new implement-plan-style skill that uses Claude Code **dynamic
workflows** as the backing orchestrator. Today's `/implement-plan` enforces its
build/verify discipline through SKILL.md prose and the harness task tools —
soft enforcement the model can drift from. A workflow script holds the loop
itself: for each plan item, implement → verify → retry until green or no
progress, with the control flow in code rather than instructions.

## Constraints that shape the design

Findings from researching the workflow runtime (details in
[workflow-script-api.md](workflow-script-api.md), the full runtime contract —
Anthropic publishes no spec for the in-script API):

- A skill may invoke the Workflow tool; a skill-instructed call counts as the
  user's opt-in to multi-agent orchestration.
- **No mid-run user input.** Interactive steps — scope confirmation,
  dirty-tree decisions, review triage — must stay in the main loop. The
  workflow covers only the implement/verify grind; sign-off between stages
  means running each stage as its own workflow.
- Workflow agents are fresh-context subagents. Each plan item must become a
  self-contained prompt (plan excerpt, file list, verification command) — the
  script can't lean on the main conversation's accumulated context.
- Scripts saved to `.claude/workflows/` become `/<name>` commands and accept
  structured `args` — so the orchestration can be hand-written and versioned
  in these dotfiles rather than regenerated by the model each run, with the
  skill passing the parsed plan items as `args`.
- Sequential items can share the working tree; parallel items need
  `isolation: 'worktree'`.
- Scripts are plain JS with determinism rules (no `Date.now()`/
  `Math.random()`; `meta` must be a pure literal) because every `agent()` call
  is journaled for resume.

# Brainstorm — 2026-07-20: multi-phase orchestration (decision log)

## The idea

How to implement a multi-phase plan without the failure modes of one long
`/implement-plan` session: task-list drift, context pile-up across phases,
and the review tail getting skipped. The shape decided on: a **thin
interactive skill** for the head and tail, a **workflow script** for the
phase loop, one **fresh-context worker per phase** running a new autonomous
inner skill, and a **smart gate agent** judging each phase's outcome before
the next begins.

## Decisions

### Orchestration backbone: a workflow script, not the Task tools
- **Question:** what mechanism drives the phase loop — a skill pre-creating
  per-phase tasks with the harness Task tools, or a dynamic workflow?
- **Decision:** a versioned workflow script (in `.claude/workflows/`, per
  the constraint above) loops phases in code: worker agent → gate agent →
  continue/adjust/abort. Task tools are used only within individual scopes,
  not as the orchestration backbone.
- **Why:** the Task tools can't express the structure — `TaskCreate` has no
  position, parent, or insert-after concept and `TaskUpdate` can't reorder
  or reparent, so per-phase detail appends flat at the end of the list;
  display ordering is unreliable (claude-code#52011); and task discipline
  is prose-enforced, so the model can drift from it. In the workflow, the
  loop is code: the gate and the verification tail are unskippable
  statements rather than instructions. It also brings journal/resume and
  `meta.phases` progress grouping — the per-phase structure the flat task
  list can't display.

### Architecture: thin skill + workflow phase loop + per-phase workers
- **Question:** what structure implements a multi-phase plan?
- **Decision:** the thin skill does the interactive head (plan context,
  feature branch, parsing phases into self-contained inputs) and tail
  (reporting, deferred-finding triage, final verification); the workflow
  script runs the phase loop, spawning one fresh-context worker per phase.
  Phases run sequentially, sharing the feature branch's working tree — no
  worktree isolation.
- **Why:** the phase is the natural isolation grain — each worker starts
  fresh (no pile-up across a 5-phase run), while items within a phase stay
  together where their coupling needs shared context. Interactive decisions
  stay in the main-loop skill, the one place that can prompt the user;
  scripts have no filesystem access, so plan parsing must happen in the
  skill and travel via `args`.

### The smart gate
- **Question:** how does the run decide whether a finished phase is good
  enough to build the next phase on?
- **Decision:** after each phase, the script runs a gate agent at
  `mzizzi:complex` (Fable, high effort) with a structured verdict schema:
  **continue**, **adjust** (continue, with corrective notes the script
  threads into the next phase's prompt), or **abort** (halt with reason).
  The gate reads the worker's structured summary and can inspect the repo,
  diff, and plan itself. Its prompt biases toward abort under uncertainty.
- **Why:** a judgment-based gate catches the approach-level problems that
  rule-based field checks miss, while keeping long runs unattended-friendly
  — the user is only pulled in when something is genuinely wrong. The gate
  is a fresh-context agent but no worse informed than the main loop: the
  durable state (plan, per-phase commits, follow-ups) lives on disk. The
  `adjust` verdict makes mid-plan course correction codeable — the script
  needn't understand the correction, just transport it. Abort-biased
  calibration because abort is cheap (it asks the human) while a wrong
  continue compounds silently. One gate call per phase is cheap next to an
  Opus-tier phase implementation.

### Abort handling: terminal in v1
- **Question:** when the gate aborts, what re-entry does v1 support — the
  user resuming with fix-it comments, or overriding with "non-issue, go"?
- **Decision:** neither, yet. On abort the workflow returns the reason and
  accumulated phase summaries, the skill reports to the user, and the run
  ends. No resume/directive contract in v1; design it after hands-on
  experience shows what the touchpoint actually needs.
- **Why:** need real aborts before designing the re-entry UX. The punt is
  well-cushioned: per-phase commits leave a clean branch with all completed
  phases intact, so manual recovery (re-run the orchestrator, which can see
  what's done) is workable. The candidate designs debated — amend-on-top vs
  revert-and-redo, phase-keyed directives in `args` for cache-safe resume —
  are recorded under open questions.

### Inner skill: new dedicated `implement-phase`, not a mode on implement-plan
- **Question:** how does the per-phase worker get a non-interactive
  implement-plan variant — retrofit an "orchestrated mode" or write a new
  skill?
- **Decision:** new dedicated skill, `implement-phase`; `/implement-plan`
  stays untouched.
- **Why:** mode conditionals in skill prose ("if orchestrated, skip Step 2…")
  are the same soft-enforcement weakness being engineered away; an
  unconditional document is more reliably followed. Accepted cost: the two
  skills share much content and can drift.

### Inner engine: inline implementation + Task-list discipline
- **Question:** inside the phase worker, what enforces the
  implement→verify→review discipline — a nested per-item workflow or the
  existing inline Step-0-style task list?
- **Decision:** inline + Task list (implement-plan's current Step 0 pattern),
  no nested workflow.
- **Why:** the worker is already fresh-context, so the pile-up argument is
  spent at this layer; task discipline drifts less in a short focused
  context; per-item agents would fragment tightly coupled edits within a
  phase.

### Per-phase commits
- **Question:** when does work get committed?
- **Decision:** each phase worker commits its phase's work when it
  finishes (after review, trivial fixes, and comment cleanup).
- **Why:** effectively forced — the Codex review reads the working-tree
  diff, so phase N must be committed for phase N+1's review to see only its
  own changes. Also gives the parent clean per-phase rollback points.

### Review placement: per-phase only
- **Question:** Codex adversarial review per phase, at the end, or both?
- **Decision:** per phase, inside the worker, over that phase's diff; the
  parent's final step aggregates but does not re-review.
- **Why:** every line is reviewed once, at phase time when fixes are
  cheapest; a whole-branch re-review roughly doubles Codex cost and mostly
  re-reports logged deferrals. A final integration-focused review can be
  added later if cross-phase seams prove to be a real gap.

### Agent tier: `mzizzi:standard` for all phases
- **Question:** which tier runs the phase workers?
- **Decision:** `mzizzi:standard` (Opus, high effort) for every phase.
- **Why:** a simple uniform rule, and the worker does more than transcribe
  a spec — it triages Codex findings and judges plan deviations, which
  benefits from the stronger tier. Chosen over per-phase escalation
  (cheaper but adds orchestrator-side judgment) — quality over cost here.

### Skill family and naming
- **Question:** how are the skills organized and how does an "implement this
  plan" request route?
- **Decision:** three skills — parent orchestrator `implement-plan-workflow`
  (the thin skill; its workflow script is a fourth artifact, versioned in
  `.claude/workflows/`), autonomous inner `implement-phase`, and
  `implement-plan` unchanged. Descriptions route multi-phase whole-plan
  requests to the orchestrator and single-scope/subset runs to
  `implement-plan`.
- **Why:** same reasoning as the dedicated inner skill — separate
  unconditional documents over one skill with branching modes.

### Documented without debate (trivially resolved)
- **Branch prep:** the parent reuses implement-plan Step 2 as written
  (trunk detection, dirty-tree prompt, `<username>/<slug>` naming with
  collision suffixes) — interactive and already battle-tested.
- **Parent task list:** per-phase progress display comes from the
  workflow's `meta.phases` progress tree; the thin skill seeds Task* items
  only for its own head/tail steps (branch prep, triage, final
  verification, summary), preserving the tail-protection idea at the one
  layer still enforced by prose.
- **Inner→parent contract:** `implement-phase` returns a structured summary
  — phase status, verification result (with output on failure), commit hash,
  findings fixed/deferred counts, follow-ups added, plan deviations,
  blockers. The gate agent keys off this.
- **Parent final step:** aggregate follow-ups across phases, interactively
  surface the deferred judgment-call findings workers couldn't ask about,
  run the full verification suite once over the finished branch, and emit an
  implement-plan-Step-9-style summary. `review-comments` runs per phase
  inside `implement-phase` (comments are phase-local).
- **Invocability:** `implement-phase` is model-invocable (workers call it)
  but not a user-facing command; its description labels it the
  orchestrator's worker skill.

## Open questions

- **Abort re-entry design (deferred deliberately):** after hands-on
  experience with real aborts, design the resume touchpoint. Candidate
  semantics debated but unresolved: **amend** (corrective agent on top of
  the phase commit — cheap, right for localized issues) vs **redo** (revert
  and re-run the phase with the user's comments — right for approach-level
  aborts), and "non-issue, proceed" overrides. Mechanism sketch: phase-keyed
  directives passed via `args` so a `resumeFromRunId` relaunch replays
  clean phases from cache and applies the directive only from the gated
  phase onward. Constraint to design around: resume is same-session only —
  cross-session re-entry must derive completed phases from git/plan state
  instead of the journal.
- **The args contract:** exactly what the thin skill passes the script, and
  the script passes each worker — plan path plus phase number, or an
  extracted self-contained excerpt (file list, testing notes, sibling-doc
  context)? Workers can read the plan themselves, which argues for path +
  phase id + branch name + prior-phase notes (including gate `adjust`
  output).
- **Gate inputs and calibration:** what the gate agent is given vs told to
  fetch itself, and how its abort bias is tuned so it neither rubber-stamps
  nor cries wolf — expect prompt iteration once real runs exist.
